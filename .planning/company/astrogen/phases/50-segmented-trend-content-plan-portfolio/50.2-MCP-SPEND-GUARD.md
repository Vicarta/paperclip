# Phase 50.2: Semantic Core MCP Spend Guard

## Incident

Paperclip requested bounded trend and semantic validation, but provider execution expanded beyond the intended unit of work.

- 2026-07-20: a five-phrase validation path correlated with 13,917 provider log rows and 3,214 unique keywords. The largest burst processed 2,846 unique keywords across geo/global Search Volume and Live Search Intent.
- 2026-07-23: another five-phrase validation processed roughly 105 registered project keywords, while Trend research sent long LLM research instructions directly to Google Organic Live Advanced.
- Provider costs were not recorded in Paperclip at run completion; accounting depended on a later import step.

## Root Causes

1. Trend query plans were trusted as search queries without a deterministic query-shape gate.
2. Trend search used Google Organic Live Advanced instead of Standard Queue Regular.
3. Paperclip defaulted omitted semantic mode to live and cache mode to read_write.
4. Autonomous routines explicitly requested live, refresh, repeated waves, and hard inventory completion.
5. The deployed candidate workflow did not reliably prove exact-candidate isolation before provider execution.
6. Cost accounting happened too late to act as an operational circuit breaker.

## Invariants

- Remote Semantic Core and Paperclip plugin provider locks are independent and fail closed.
- Omitted semantic mode is mock; omitted trend mode is fixture.
- Paperclip paid semantic execution requires operator policy `approved_candidate_batch`.
- Paid agent runs contain 1-10 exact `candidate_keywords`.
- Autonomous provider runs use Standard Queue, disable Search Intent and content parsing, and forbid refresh/bypass.
- Live trend runs use private-project cache, at most 12 research queries and 30 sources; Astrogen defaults are 6 and 20.
- Every Trend provider SERP query contains at most four words. Blank,
  instruction-shaped, over-100-character, or five-word-and-longer queries are
  rejected before provider access.
- Trend SERP uses Standard Queue Regular, not Live Advanced.
- `run-layer-and-wait` fetches `get_run_costs` before completion and records actual provider cost when available.
- A provider lock creates one deduplicated monitored wait. It does not trigger retries, owner email, Telegram errors, fixture substitution, or stop independent portfolio work.
